# Lab 4 Specification: Agent Traffic Monitor

## 1. Purpose

Build a small local dashboard for inspecting traffic between an AI coding agent and its model.
It is a teaching and debugging tool—not a production observability system—and must fit a 90-minute lab without interfering with proxy traffic.

## 2. Proxy compatibility gate

Compatibility with the actual Lab 4 proxy is a must-have requirement.
Before implementation, inspect the supplied proxy code and run it to determine:

- where model requests, responses, and errors can be observed;
- the real payload shapes and available correlation identifiers;
- whether tool calls and results are embedded in messages or exposed separately;
- which HTTP routes or other integration points already exist; and
- whether the proxy supports streaming, polling, or neither.

This workspace currently contains no proxy implementation to verify, so this specification does not mandate route names, a framework, or Server-Sent Events (SSE).
Use the proxy's existing interface where practical, add only the smallest monitoring adapter, and do not replace, delay, mutate, replay, or cancel normal traffic.
Document the chosen integration point and live-update mechanism in the completed lab README.

## 3. Must-have scope

- One locally running proxy/monitor and one browser dashboard.
- A bounded, in-memory buffer of captured traffic for the current process only.
- Initial display of already buffered items and automatic display of new items.
- Visibility into system prompts, conversation history, model requests and responses, tool definitions, tool calls, and tool results when present in captured traffic.
- A chronological list with concise summaries and expandable, readable JSON.
- Event-type filtering, text search, connection/error states, and a clear-events action.
- Basic credential redaction and safe rendering of all captured content.

## 4. Out of scope

- Authentication, multiple users or proxies, remote deployment, and production hardening.
- Databases, files, browser storage, or restoring captured traffic after restart.
- Editing, replaying, exporting, or forwarding traffic from the dashboard.
- Charts, cost analytics, saved queries, advanced filters, pagination, and virtual scrolling.
- Provider-perfect parsing, configurable redaction policies, and automatic secret detection.

## 5. Monitor data model

The adapter must map real proxy data into a small internal view model without discarding inspectable content or changing the upstream format.

Each displayed item has:

| Field | Requirement |
| --- | --- |
| `id` | Stable unique string when available; otherwise generated by the monitor. |
| `timestamp` | Observed time; preserve an invalid or missing original value in details. |
| `type` | `model_request`, `model_response`, `tool_call`, `tool_result`, `error`, or `unknown`. |
| `data` | Complete captured payload or closest JSON-safe representation, after credential redaction. |
| `requestId` | Correlation value when the proxy provides one. |
| `summary` | Short label derived from available content. |
| `metadata` | Optional model, status, duration, usage, or error information actually observed. |

Unknown fields and event types must remain visible in raw details.
The monitor must not invent unavailable prompts, messages, tool data, metadata, or correlations.
If a captured body is not valid JSON, retain it as text and mark it as unparsed.

For a model request, preserve when present:

- system/developer instructions and the ordered user/assistant/tool conversation history;
- model name and relevant request options; and
- complete tool definitions, including names, descriptions, and input schemas.

For a model response, preserve its messages or content, finish/status information, usage, and requested tool calls when present.
For a tool call, preserve the tool name, call ID, and complete arguments.
For a tool result, preserve the call ID, returned content, and error indication when present.

## 6. Live data delivery

Choose the simplest mechanism supported by the inspected proxy:

1. Use an existing live stream if the proxy already exposes a suitable one.
2. Otherwise poll an existing or minimal monitor endpoint at about two-second intervals.
3. Add a minimal local stream only if it fits the proxy's stack; SSE is optional, not assumed.

The dashboard must load the current buffer before or while starting live updates.
Items must appear oldest first and must not be duplicated across initial load and later updates.
The UI must show `Live`, `Polling`, or `Disconnected`, as applicable to the chosen mechanism.
A failed update must not remove traffic already displayed.
The buffer must have a reasonable fixed limit; when full, discard the oldest items.

Any added monitor routes must follow the starter proxy's conventions.
At minimum, the integration must support reading buffered items and clearing them; exact methods and paths are implementation decisions after inspection.

## 7. Dashboard behavior

Use one responsive page with a header, compact filter bar, and event timeline.
The header shows `Agent Traffic Monitor`, connection state, visible/total count, a sensitivity notice, and `Clear events`.
The filter bar provides an all/type filter, case-insensitive text search, and `Clear filters`.
Type and text filters combine with AND logic and affect only the displayed list.
Search must cover summaries and serialized content, including prompts, tool names, and request IDs.

Each collapsed item shows its type, local timestamp, summary, and available model or correlation information.
Missing optional values are omitted rather than rendered as `null` or `undefined`.
Selecting an item expands or collapses it.

Expanded details must:

- label recognizable system, developer, user, assistant, and tool messages;
- expose tool definitions, tool-call arguments, tool results, and response content when present;
- always include the complete redacted raw item as indented, monospace JSON or escaped plain text; and
- wrap or scroll long values without widening the page.

The page must remain usable at laptop width and approximately 375 px width.
An empty buffer shows: `No traffic captured yet. Send a request through the proxy.`
Clearing requires a lightweight confirmation, clears both server memory and the page, and does not stop future capture.

## 8. Essential error handling

- Initial-load failure: show a concise error and a retry control.
- Live-update failure: retain existing items, show `Disconnected`, and retry or allow retry.
- Invalid item or timestamp: show a fallback item and preserve inspectable source data.
- Unknown type: use neutral styling and allow normal expansion and search.
- Per-item rendering failure: isolate it so the rest of the timeline still works.
- Proxy/upstream error: capture it when observable, but preserve the proxy's normal error behavior.

## 9. Privacy and safety

- Bind monitor access to localhost by default.
- Keep captured items only in bounded server memory; do not write them to disk, analytics, `localStorage`, or `sessionStorage`.
- Remove or replace authorization headers, API keys, cookies, and proxy credentials with `[REDACTED]` before buffering or sending data to the browser.
- Treat payloads as untrusted text: escape them and never inject them as executable HTML.
- Display `Local session only — captured content may be sensitive.`
- Manual clear and process restart must remove all captured items.

## 10. Acceptance criteria

The must-have implementation is complete when these checks pass with fixtures shaped like the actual proxy traffic:

- [ ] The README identifies the inspected proxy integration point, actual payload shape, and selected update mechanism; it does not claim unsupported SSE or routes.
- [ ] Three buffered items appear once, oldest first, when the dashboard opens.
- [ ] A newly captured request or response appears without a page refresh within one update interval.
- [ ] Re-reading the same buffered item does not create a duplicate.
- [ ] If live updates fail, existing items remain visible, the state becomes `Disconnected`, and retry is possible.
- [ ] A request fixture exposes its system prompt, ordered conversation history, model request data, and complete tool definitions.
- [ ] Response, tool-call, and tool-result fixtures expose their content, arguments/results, IDs, and error/status data when provided.
- [ ] Every item expands to readable raw JSON or escaped text, including fields not specially formatted by the UI.
- [ ] Long or nested data remains readable without horizontal page overflow.
- [ ] Type filtering and case-insensitive search work independently and together without deleting buffered data.
- [ ] Clearing filters restores all items; confirming clear empties server memory and later traffic still appears.
- [ ] Empty, unknown, malformed, missing-field, invalid-time, and proxy-error fixtures do not crash the page.
- [ ] Script or HTML content in a payload is displayed as text and never executes.
- [ ] Credential fixtures show `[REDACTED]`, and no captured traffic survives process restart or appears in persistent storage.
- [ ] Normal proxied model requests still succeed with monitoring enabled.

## 11. Optional improvements

Only attempt these after every acceptance criterion passes:

- Syntax coloring or copy-to-clipboard for JSON.
- Automatic reconnection with backoff or a stream-to-polling fallback.
- Expand/collapse all controls or improved semantic formatting for provider-specific payloads.
- Configurable buffer size or additional metadata already available from the proxy.

## 12. Deliverable

The eventual deliverable is a locally runnable proxy-compatible dashboard plus brief setup and run instructions; this revision specifies it but does not implement it.
